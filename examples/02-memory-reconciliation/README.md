# 02 · When a new memory should not erase an old one

“Use Python for this prototype” is not the same as “I now prefer Python.”

**Pattern:** Scoped correction, temporary exceptions, and deliberate abstention.

## Why this decision matters

Blindly overwriting a preference turns a one-off request into a permanent personality change. The relationship between facts matters more than recency alone.

## Run it

From the repository root:

```sh
npm start -- run 02
npm start -- request 02 --case permanent-correction
npm start -- run 02 --case permanent-correction --live
```

The first command uses authored response fixtures. The last needs a TypeSafe API key and makes a real request. No command performs the proposed downstream action.

## Read the evidence

Example input: **permanent-correction**.

```json
{
  "stored": {
    "text": "I prefer TypeScript for personal projects."
  },
  "incoming": {
    "text": "Update my default: I now prefer Python for personal projects instead of TypeScript."
  }
}
```

## Ask focused questions

### `relationship` · choice

How does `incoming.text` relate to `stored.text` for the same user? Respect time and project qualifiers.

```json
{
  "correction": "Explicitly replaces the standing preference.",
  "exception": "Applies only to a particular task or time.",
  "duplicate": "Repeats the existing preference.",
  "unrelated": "Does not establish a relationship, or evidence is insufficient."
}
```

### `secret` · noul

Does `incoming.text` contain an actual credential, access token, password, or private key rather than merely mention one?


All these questions see the same state independently. None sees another question's answer. Review [example.mjs](example.mjs) for the policy and [cases.mjs](cases.mjs) for the full case set.

## Follow the policy

The authored fixture produces this application result:

```json
{
  "action": "propose-replacement",
  "reason": "Keep the original evidence and scope with any proposed memory change."
}
```

The `reason` is written by application code, not generated by Jev. Fixture numbers illustrate policy branches; they are not measurements or predictions of model behavior.

## Try the contrasting cases

| Case | What changes | Intended policy outcome |
| :-- | :-- | :-- |
| `permanent-correction` | An explicit standing-preference update. | `propose-replacement` |
| `temporary-exception` | Preserve the durable preference. | `keep-scoped` |
| `unclear-referent` | The collection deliberately includes an abstention. | `review` |

These intended outcomes are author judgments. A live disagreement is evidence to inspect, not a result to quietly relabel.

## Change one thing

Change “for this weekend only” to “from now on.” Add two contradictory updates without dates. Decide what evidence should be required before replacing either memory.

Edit the case state, inspect the request, then run with `--live` to see what Jev does. Editing only the state in fixture mode does **not** change its scripted response. Change fixture values separately when testing a policy branch.

## Where it stops

Returns a proposed memory operation; no Engram database is connected or mutated. Authorization and retention rules belong to the memory host.

**Known failure mode:** Pronouns, sarcasm, and missing dates can hide whether a correction is permanent. Keep both records when the relationship is uncertain.

The included baseline is intentionally limited. Its purpose is to expose a particular shortcut, not to represent the strongest alternative. See [evaluation notes](../../docs/evaluation.md).
