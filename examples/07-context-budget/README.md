# 07 · Spend context on evidence, not repetition

A relevant paragraph can still be redundant. A short constraint can still be mandatory.

**Pattern:** Two independent scores followed by deterministic budget packing.

## Why this decision matters

Separating usefulness from novelty avoids repeatedly selecting the same evidence. Mandatory constraints bypass ranking entirely.

## Run it

From the repository root:

```sh
npm start -- run 07
npm start -- request 07 --case useful-over-short
npm start -- run 07 --case useful-over-short --live
```

The first command uses authored response fixtures. The last needs a TypeSafe API key and makes a real request. No command performs the proposed downstream action.

## Read the evidence

Example input: **useful-over-short**.

```json
{
  "task": "Investigate the hanging database request.",
  "alreadyKnown": "The request hangs; API compatibility is required.",
  "budgetCharacters": 150,
  "snippets": [
    {
      "id": "constraint",
      "mandatory": true,
      "text": "The fix must preserve the public API."
    },
    {
      "id": "trace",
      "mandatory": false,
      "text": "Trace: the request hangs while waiting for an unreleased connection."
    },
    {
      "id": "launch",
      "mandatory": false,
      "text": "Marketing wants a launch announcement by Friday."
    },
    {
      "id": "repeat",
      "mandatory": false,
      "text": "Another copy of the already supplied incident summary."
    }
  ]
}
```

## Follow the policy

The authored fixture produces this application result:

```json
{
  "action": "pack",
  "reason": "Pinned constraints first; confident, useful, novel evidence next.",
  "selected": [
    "constraint",
    "trace"
  ],
  "characters": 107,
  "context": "The fix must preserve the public API.\n\nTrace: the request hangs while waiting for an unreleased connection."
}
```

The `reason` is written by application code, not generated by Jev. Fixture numbers illustrate policy branches; they are not measurements or predictions of model behavior.

## Try the contrasting cases

| Case | What changes | Intended policy outcome |
| :-- | :-- | :-- |
| `useful-over-short` | Choose a trace over shorter launch chatter. | `pack` |
| `uncertain-evidence` | Keep the constraint when the trace scores are uncertain. | `pack` |
| `impossible-budget` | Fail explicitly instead of losing a required constraint. | `increase-budget` |

These intended outcomes are author judgments. A live disagreement is evidence to inspect, not a result to quietly relabel.

## Change one thing

Shrink the character budget below the mandatory constraint. Then replace an irrelevant snippet with genuinely new evidence and inspect the selected IDs, not just the action name.

Edit the case state, inspect the request, then run with `--live` to see what Jev does. Editing only the state in fixture mode does **not** change its scripted response. Change fixture values separately when testing a policy branch.

## Where it stops

Uses a character budget for the joined snippet text, not a model token budget. Greedy packing is a transparent heuristic, not an optimal solver.

**Known failure mode:** Two individually useful snippets can duplicate each other. This small example scores novelty against alreadyKnown, not pairwise redundancy.

The included baseline is intentionally limited. Its purpose is to expose a particular shortcut, not to represent the strongest alternative. See [evaluation notes](../../docs/evaluation.md).
