# 03 · The release note that outran the evidence

A passing unit test becomes “zero regressions on every supported platform.”

**Pattern:** Batch independent claim checks; return exact claim IDs.

## Why this decision matters

Review each supplied claim against its cited artifact. This avoids asking a model to invent a critique or summarize away the unsupported part.

## Run it

From the repository root:

```sh
npm start -- run 03
npm start -- request 03 --case overclaim
npm start -- run 03 --case overclaim --live
```

The first command uses authored response fixtures. The last needs a TypeSafe API key and makes a real request. No command performs the proposed downstream action.

## Read the evidence

Example input: **overclaim**.

```json
{
  "artifact": "PASS: 18 unit tests on Linux, Node 22. Browser tests and load tests were not run.",
  "claims": [
    {
      "id": "unit",
      "text": "18 unit tests passed on Linux with Node 22."
    },
    {
      "id": "universal",
      "text": "Zero regressions across every supported platform."
    },
    {
      "id": "latency",
      "text": "Checkout is 40% faster under production load."
    }
  ]
}
```

## Ask focused questions

### `claim_0` · noul

Does the supplied text in `artifact` substantiate the entire claim at `claims[0].text`, including scope and qualifiers? Missing evidence is not support.

All these questions see the same state independently. None sees another question's answer. Review [example.mjs](example.mjs) for the policy and [cases.mjs](cases.mjs) for the full case set.

## Follow the policy

The authored fixture produces this application result:

```json
{
  "action": "revise",
  "reason": "Return claim IDs for an editor to inspect.",
  "unsupported": [
    "universal",
    "latency"
  ]
}
```

The `reason` is written by application code, not generated by Jev. Fixture numbers illustrate policy branches; they are not measurements or predictions of model behavior.

## Try the contrasting cases

| Case | What changes | Intended policy outcome |
| :-- | :-- | :-- |
| `overclaim` | One narrow result cannot support a universal claim. | `revise` |
| `bounded-claim` | Qualifiers preserve what the artifact actually establishes. | `ready-for-review` |
| `missing-artifact` | The author saying it works is not the requested test evidence. | `revise` |

These intended outcomes are author judgments. A live disagreement is evidence to inspect, not a result to quietly relabel.

## Change one thing

Change “all supported platforms” to the exact platform named in the artifact. Add an artifact that is internally contradictory and inspect which claim IDs are flagged.

Edit the case state, inspect the request, then run with `--live` to see what Jev does. Editing only the state in fixture mode does **not** change its scripted response. Change fixture values separately when testing a policy branch.

## Where it stops

Checks support in the provided text, not the truth or authenticity of the underlying artifact. It does not execute tests or publish release notes.

**Known failure mode:** A fabricated artifact can still support a fabricated claim. Provenance must be verified outside this example.

The included baseline is intentionally limited. Its purpose is to expose a particular shortcut, not to represent the strongest alternative. See [evaluation notes](../../docs/evaluation.md).
