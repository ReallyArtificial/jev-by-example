# 06 · The retry that creates a second invoice

A timeout after a write means “unknown,” not necessarily “failed.”

**Pattern:** Use transaction evidence before classifying recovery options.

## Why this decision matters

Retries are a workflow decision. Transport symptoms cannot tell you whether a remote side effect already happened.

## Run it

From the repository root:

```sh
npm start -- run 06
npm start -- request 06 --case read-unavailable
npm start -- run 06 --case read-unavailable --live
```

The first command uses authored response fixtures. The last needs a TypeSafe API key and makes a real request. No command performs the proposed downstream action.

## Read the evidence

Example input: **read-unavailable**.

```json
{
  "operation": {
    "name": "read_catalog",
    "sideEffect": false
  },
  "outcome": "failed",
  "attempt": 1,
  "maxAttempts": 3,
  "error": "503: catalog shard temporarily unavailable; try again later."
}
```

## Ask focused questions

### `cause` · choice

What recovery category is supported by `error` and `operation`? Do not infer missing server state.

```json
{
  "transient": "A temporary availability or rate-limit problem.",
  "repair": "Bad input or configuration needs correction.",
  "credentials": "Authentication or authorization needs attention.",
  "unknown": "Insufficient or conflicting evidence."
}
```


All these questions see the same state independently. None sees another question's answer. Review [example.mjs](example.mjs) for the policy and [cases.mjs](cases.mjs) for the full case set.

## Follow the policy

The authored fixture produces this application result:

```json
{
  "action": "retry-with-backoff",
  "reason": "Propose a path; the executor retains control."
}
```

The `reason` is written by application code, not generated by Jev. Fixture numbers illustrate policy branches; they are not measurements or predictions of model behavior.

## Try the contrasting cases

| Case | What changes | Intended policy outcome |
| :-- | :-- | :-- |
| `ambiguous-write` | Never let classification override an unknown write outcome. | `reconcile` |
| `read-unavailable` | A bounded retry for a read. | `retry-with-backoff` |
| `timeout-configuration` | The word timeout is part of a validation error. | `repair-input` |
| `budget-exhausted` | Repeated transients still have a finite budget. | `stop` |

These intended outcomes are author judgments. A live disagreement is evidence to inspect, not a result to quietly relabel.

## Change one thing

Change a failed read into a write with an unknown outcome. Confirm that the recovery path becomes reconciliation without consulting the model.

Edit the case state, inspect the request, then run with `--live` to see what Jev does. Editing only the state in fixture mode does **not** change its scripted response. Change fixture values separately when testing a policy branch.

## Where it stops

Only proposes a recovery path. Never issues a retry, invoice, payment, or external write. Idempotency must be enforced by the actual service.

**Known failure mode:** Logs can omit the committed write. An unknown outcome stays a reconciliation task even if a model is certain it was transient.

The included baseline is intentionally limited. Its purpose is to expose a particular shortcut, not to represent the strongest alternative. See [evaluation notes](../../docs/evaluation.md).
