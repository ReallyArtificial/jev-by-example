# 05 · HTTP 200 is not task completion

A tool says success while quietly returning a truncated or irrelevant result.

**Pattern:** Deterministic transport checks plus semantic postconditions.

## Why this decision matters

Agents often treat the absence of an exception as success. Check whether the result satisfies the original request, not just the transport.

## Run it

From the repository root:

```sh
npm start -- run 05
npm start -- request 05 --case acknowledgement
npm start -- run 05 --case acknowledgement --live
```

The first command uses authored response fixtures. The last needs a TypeSafe API key and makes a real request. No command performs the proposed downstream action.

## Read the evidence

Example input: **acknowledgement**.

```json
{
  "request": "Return the failed checkout IDs for September 21.",
  "result": {
    "status": 200,
    "truncated": false,
    "text": "Your September 21 checkout report has been queued. Check back later."
  }
}
```

## Ask focused questions

### `satisfies` · noul

Does `result.text` provide the specific deliverable in `request`, rather than an acknowledgement, plan, or unrelated summary?

### `matches_scope` · noul

Does the time period and subject in `result.text` match `request`?


All these questions see the same state independently. None sees another question's answer. Review [example.mjs](example.mjs) for the policy and [cases.mjs](cases.mjs) for the full case set.

## Follow the policy

The authored fixture produces this application result:

```json
{
  "action": "incomplete",
  "reason": "Both the deliverable and its scope must be supported."
}
```

The `reason` is written by application code, not generated by Jev. Fixture numbers illustrate policy branches; they are not measurements or predictions of model behavior.

## Try the contrasting cases

| Case | What changes | Intended policy outcome |
| :-- | :-- | :-- |
| `acknowledgement` | A queued job is not its output. | `incomplete` |
| `wrong-day` | The right deliverable for the wrong period. | `incomplete` |
| `complete` | A bounded result with matching scope. | `accept-candidate` |

These intended outcomes are author judgments. A live disagreement is evidence to inspect, not a result to quietly relabel.

## Change one thing

Return a complete report for the wrong date, then a partial report for the right date. Distinguish a semantic mismatch from the deterministic truncated flag.

Edit the case state, inspect the request, then run with `--live` to see what Jev does. Editing only the state in fixture mode does **not** change its scripted response. Change fixture values separately when testing a policy branch.

## Where it stops

A possible pattern for tests around MCP tools. No MCP-Jest integration is installed, and the proposed result is not proof of task completion.

**Known failure mode:** A server can misreport completeness or fabricate content. An independent source or executable assertion is stronger where available.

The included baseline is intentionally limited. Its purpose is to expose a particular shortcut, not to represent the strongest alternative. See [evaluation notes](../../docs/evaluation.md).
