# 08 · The handoff that forgot “do not deploy”

A fluent summary can preserve the story while losing the obligations.

**Pattern:** Check a compressed handoff against an explicit obligation ledger.

## Why this decision matters

A receiving agent needs constraints and uncertainty, not just progress. Check each required fact independently before accepting compression.

## Run it

From the repository root:

```sh
npm start -- run 08
npm start -- request 08 --case lost-negation
npm start -- run 08 --case lost-negation --live
```

The first command uses authored response fixtures. The last needs a TypeSafe API key and makes a real request. No command performs the proposed downstream action.

## Read the evidence

Example input: **lost-negation**.

```json
{
  "obligations": [
    {
      "id": "compatibility",
      "text": "Preserve the existing public API."
    },
    {
      "id": "unverified",
      "text": "The proposed fix has not been verified on Windows."
    },
    {
      "id": "no-deploy",
      "text": "Prepare a patch; do not deploy it."
    }
  ],
  "handoff": "Keep the public interface compatible. Windows remains untested. The patch is ready to deploy."
}
```

## Ask focused questions

### `kept_0` · noul

Does `handoff` preserve the meaning of `obligations[0].text`, including prohibitions and uncertainty, without contradicting it?

### `kept_1` · noul

Does `handoff` preserve the meaning of `obligations[1].text`, including prohibitions and uncertainty, without contradicting it?

### `kept_2` · noul

Does `handoff` preserve the meaning of `obligations[2].text`, including prohibitions and uncertainty, without contradicting it?


All these questions see the same state independently. None sees another question's answer. Review [example.mjs](example.mjs) for the policy and [cases.mjs](cases.mjs) for the full case set.

## Follow the policy

The authored fixture produces this application result:

```json
{
  "action": "repair-handoff",
  "reason": "Carry explicit constraints and unresolved checks into the next context.",
  "missing": [
    "no-deploy"
  ]
}
```

The `reason` is written by application code, not generated by Jev. Fixture numbers illustrate policy branches; they are not measurements or predictions of model behavior.

## Try the contrasting cases

| Case | What changes | Intended policy outcome |
| :-- | :-- | :-- |
| `lost-negation` | Progress prose quietly flips a restriction. | `repair-handoff` |
| `faithful-paraphrase` | Meaning is preserved without copying verbatim. | `handoff-candidate` |
| `erased-uncertainty` | An unknown becomes an asserted success. | `repair-handoff` |

These intended outcomes are author judgments. A live disagreement is evidence to inspect, not a result to quietly relabel.

## Change one thing

Paraphrase the prohibition without losing it. Then move “not verified” to “verified” and inspect the missing obligation IDs.

Edit the case state, inspect the request, then run with `--live` to see what Jev does. Editing only the state in fixture mode does **not** change its scripted response. Change fixture values separately when testing a policy branch.

## Where it stops

Does not generate a summary or execute a handoff. The obligation ledger is supplied by the caller and may itself be incomplete.

**Known failure mode:** If a constraint was never added to the ledger, this checker cannot notice its disappearance.

The included baseline is intentionally limited. Its purpose is to expose a particular shortcut, not to represent the strongest alternative. See [evaluation notes](../../docs/evaluation.md).
